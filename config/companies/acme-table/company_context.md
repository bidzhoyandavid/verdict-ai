## Продукт

Продукт: Acme Table разрабатывает AI-агента для анализа A/B-тестов. Агент принимает данные теста (метрики, группы), проводит статистический анализ и выдаёт вывод: победитель / не значимо / нужно больше данных. Вся статистика реализована в собственном Python-пакете abex, агент выступает только оркестратором поверх него (LangGraph — управление состояниями и вызовами инструментов, LangChain — обвязка LLM и tools, Streamlit — чат-интерфейс с загрузкой файла и графиками на plotly). Пайплайн жёстко структурирован по узлам: загрузка данных → валидация и профилирование метрики → проверка SRM → подбор теста (selector) → расчёт теста → проверка guardrail-метрик → формирование инсайта для пользователя, с уточняющими вопросами при нехватке данных вместо угадывания. Часть функциональности пакета abex (байесовский подход, sequential-тестирование, CUPED, детект novelty-эффекта, разбивка по сегментам) пока не реализована (заглушки), и агент должен явно сообщать об этом, а не подменять расчётом собственного изобретения. Модель компании (B2B/B2C) не указана.

## Ключевые метрики

Ключевые метрики: в форме и в ходе обсуждения бизнес-метрики компании (например, целевые продуктовые/финансовые показатели Acme Table) не указаны. Известно, что сам инструмент оперирует статистическими величинами, которые обязательны в выводе по любому тесту: p-value, effect size (в т.ч. cohen's d, доверительный интервал), результат проверки SRM, результат проверки guardrail-метрик (например, latency, errors — если они присутствуют в данных) и, при множественных метриках, скорректированный p-value (поправка Бонферрони). Какие именно бизнес- или продуктовые метрики являются ключевыми для компании — не указано.

## Специфика домена

Специфика домена: явных данных о сезонности, длительности цикла принятия решений и регуляторных ограничениях компания не предоставила — не указано. Из технического описания следует ряд обязательных правил, влияющих на интерпретацию результатов A/B-тестов в этом продукте: проверка SRM (alpha=0.001) является гейтом — при её срабатывании эксперимент считается невалидным и дальнейший статистический вывод не производится; при анализе более одной метрики обязательна поправка на множественные сравнения (Bonferroni); guardrail-метрики проверяются параллельно с основной метрикой, и их нарушение должно отражаться в выводах даже при статистически значимом позитивном эффекте по основной метрике; effect size всегда сообщается вместе с p-value, а не отдельно. Строгого учёта peeking и novelty-эффекта пакет пока не поддерживает — агент может дать только эвристическое текстовое предупреждение (например, если есть timestamp и тест короче ~1-2 недель), без формального расчёта. Выбор метода теста агент не определяет самостоятельно, а полностью доверяет модулю selector; если подходящий метод не найден, следует уточняющий вопрос пользователю вместо предположений.
